# ADR-021 — Автообновление по GitHub Releases и полноценная portable-версия

> Статус: принято (CR-014) · Дата: 2026-10-13 · Связанное: [ADR-018](./ADR-018-tauri-desktop-exe.md),
> [ADR-017](./ADR-017-single-file-executable.md), [FR-709](../fr/FR-700-nfr.md)

## Контекст

Запрос пользователя (CR-014): «добавить обновление в сервис на основании новых релизов в GitHub,
чтобы не приходилось по несколько раз устанавливать одно и то же; и можно ли сделать сразу portable
версию, без потребности в установке».

К этому моменту (v0.10.1) дистрибуция уже двухканальная: NSIS-установщик
`Avizis_x.y.z_x64-setup.exe` + `avizis-portable-windows-x64.zip` в каждом GitHub Release. Проблема
операционная: **каждое обновление — ручной цикл** «увидеть релиз → скачать → установить поверх»;
при частых итерациях прототипа (v0.10.0 → v0.10.1 за день) это основной источник трения.

Ограничения и факты:

1. **Portable-архив уже собирается CI** — распаковал и запустил, установки нет; но и он не умеет
   обновляться: замена файлов руками, никакой сигнализации о новой версии.
2. **Приложение = два exe в одном каталоге** (`avizis.exe` + `avizis-engine.exe`) — и в установленной
   (NSIS кладёт их в `%LocalAppData%\Programs\Avizis`), и в portable-версии. Данные (история, ключи
   LLM, кэши) живут в каталоге ОС (`app_data_dir`, ADR-018) — переживают любую подмену файлов.
3. **`tauri-plugin-updater`** (официальный путь) требует: подпись minisign (генерация ключей,
   хранение приватного секрета в CI-секретах), артефакты-установщики и `latest.json`; на Windows
   применение обновления = тихий запуск установщика — **для portable-распаковки это не годится**
   (установщик поставит копию в Program Files, распаковка не обновится).
4. Проверка обновления — один HTTP-запрос к публичному GitHub API при старте; лимит
   неаутентифицированных запросов 60/час на IP — для десктоп-приложения с запасом.

## Решение

**Собственный апдейтер в Tauri-оболочке: `releases/latest` → сравнение версий → скачивание
портативного zip → подмена файлов рядом с exe → автоперезапуск. Один код-путь для установленной
и portable-версии** (факт 2: обе — «два exe в каталоге», разница только в наличии деинсталлятора,
который подмену не ломает).

Слои:

| Слой | Где | Что делает |
|---|---|---|
| Ядро `src-tauri/updater-core/` (чистый Rust) | `lib.rs`, `fs.rs` | сравнение версий (`is_newer`, покомпонентно, короткие хвосты = 0); разбор JSON `releases/latest` (`extract_release`: черновики/пререлизы/ассент-мусор → ошибки); план подмены (`plan_files`: движок → прочее → оболочка последней, только плоские имена, защита от zip-slip); распаковка и подмена файлов (`extract_flat`, `perform_swap`, бэкапы `*.old`, `cleanup_backups`) — всё покрыто юнит/интеграционными тестами `cargo test` на любой платформе |
| Tauri-слой `src-tauri/src/updater.rs` (тонкий) | команды | `check_updates` (GitHub API через reqwest/rustls, ошибки — в поле `error`, не исключениями); `apply_update` (стриминговое скачивание с прогрессом `update:progress`, сверка размера с метаданными релиза, гашение движка, вызов ядра подмены, spawn нового exe + `app.exit(0)`); защита от параллельного запуска `AtomicBool` |
| UI `src/lib/avizis/updater.ts` + `UpdateBadge` | футер | тихая авто-проверка при старте → тост «Доступна версия vX.Y.Z» с кнопкой «Обновить»; бейдж в футере («обновить до vX.Y.Z» / «обновление… N%» / «не удалось»); ручная проверка по кнопке-иконке; прогресс тостом (МБ + %, установка, перезапуск); invoke-обрыв при перезапуске трактуется как успех |

Ключевые детали механизма:

- **Порядок подмены**: движок первым (его процесс уже погашен, файл свободен), оболочка последней
  (rename живого exe на Windows разрешён) — при сбое посередине на месте остаются согласованные
  новые файлы, перезапуск доканчивает обновление.
- **Бэкапы**: старые файлы → `*.old` рядом, удаляются best-effort при следующем старте (`setup`).
- **Данные не трогаются**: движок читает `AVIZIS_DATA_DIR` (каталог ОС) — история и ключи переживают
  обновление без переустановки; это и есть «не приходится устанавливать одно и то же».
- **Portable-контракт в браузере**: `?update-mock=1` (как `?port=` для движка, ADR-018) —
  детерминированный сценарий обновления без Tauri для E2E/отладки UI.
- **Portable-архив дополняется README.txt** (запуск, WebView2, где данные, как обновляться).

Альтернативы, отклонённые:

- **`tauri-plugin-updater`** — см. ограничение 3: подпись-секрет в CI, установщик-центричность,
  portable не обновляет. Вернуться к нему имеет смысл при появлении кодовой подписи приложения.
- **Обновление через chocolatey/winget/scoop** — внешние каналы для прототипа, ручной ритзм релизов
  тот же.
- **Self-hosted latest.json** — ещё один эндпоинт для поддержки; GitHub Releases уже «канал
  стабильных версий» с CDN и историей.

## Последствия

- Пользователь обновляется одним кликом из приложения (или соглашается на тост при старте):
  скачивание с прогрессом, подмена, перезапуск — история/настройки/ключи на месте.
- **Переход v0.10.1 → v0.11.0 — последняя ручная установка** (в v0.10.1 апдейтера нет); дальше —
  только автообновления.
- Целостность без подписи: HTTPS GitHub + сверка размера ассета с метаданными релиза + отказ
  zip-крейта от небезопасных путей. Подмена канала (compromised release) не отбивается — принятый
  риск прототипа, зафиксирован для будущего решения (кодовая подпись + `latest.json`).
- Проверка при старте — 1 запрос к GitHub API (неаутентифицированный, 60/час/IP); при rate-limit
  проверка тихо скипается, ручная кнопка показывает понятную ошибку.
- Обновлённый registry NSIS-установки показывает прежнюю версию до следующей «полной» установки —
  косметика для панели «Установка и удаление программ», работа приложения не затрагивается.
- CI-пайплайн не меняется концептуально: тот же zip-ассет теперь источник и для автообновления
  (порядок байтов релиза = порядок байтов обновления).
