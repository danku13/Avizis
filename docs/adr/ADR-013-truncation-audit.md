# ADR-013: Аудит усечений структурных лимитов

> Тип: ADR · Статус: принято (реализация — [CR-008](../cr/CR-008-truncation-audit.md)) · Связанное:
> [ADR-011](./ADR-011-unbounded-questions-soft-volumes.md), [FR-603/604](../fr/FR-600-history-and-log.md)

**Контекст.** Санитайзеры вывода LLM применяют структурные лимиты **молча**, без записей в журнал
аудита: усечение узлов плана >12, зависимостей узла >5, вариантов развилки >4, шагов ветки >3,
зависимостей после перепривязки >12, деградация «развилки» с <2 вариантами в обычный шаг,
фильтрация ссылок `dependsOn` на необъявленные узлы. Разбор реестра ограничений (задача 8) показал:
пользователь не может узнать из прогона, что план был обрезан, а потеря зависимостей при капе 5
может менять порядок выполнения. Для системы, чья ценность — прозрачность вычисления, тихие
потери недопустимы: аудита нет — доверия к replay нет.

**Решение.**
1. **Каждое усечение — запись в журнал запуска.** Используется существующий канал:
   `RunSnapshot.logs` + log-события в event-stream → записи видны в журнале событий, playback
   и MD-отчёте без изменений протокола.
2. **Формат записи**: источник (план / адаптация), что усечено, насколько (N→M), идентификаторы
   затронутых узлов. Пример: «Лимит плана: LLM вернул 15 узлов — взяты первые 12 (отброшены:
   n13 «Проверка формата», n14 «…»)».
3. **Усечения не отменяются.** Лимиты остаются санитайзерами вывода LLM (защита от разбухания
   планов, осознанно оставленная в ADR-011); меняется их видимость. Отдельный kind записи
   (`limits`) с бейджем в журнале.
4. **Санитайз плана — чистая функция.** Логика `sanitizePlan` выделяется из движка в
   `plan-sanitizer.ts` со возвратом `notes[]` (структурированный список усечений) —
   детерминированно тестируется без LLM.
5. Ярлыки title/label ≤60 и заголовок вопроса ≤40 остаются без журналирования — это
   нормализация идентификаторов на канве (ADR-011, п. 5), а не потеря данных.

**Альтернативы.** Снять лимиты — устранило бы проблему источника, но лимиты защищают от
разбухания LLM-вывода; их поднять/убрать — отдельное продуктовое решение, не требуемое для
прозрачности. Отдельный тип событий `truncation:*` в event-stream — дороже (новый тип в протоколе,
fold, UI) при той же аудит-ценности, чем log-канал.

**Последствия.** Журнал честно показывает все структурные потери плана и адаптаций; объём записей
незначителен (усечения редки); replay и MD-отчёт наследуют их автоматически. Побочный эффект:
заметность усечений в аудите делает качество санитайза измеримым и может мотивировать пересмотр
величины лимитов — уже как осознанное решение на данных, а не молчаливый дефект.
