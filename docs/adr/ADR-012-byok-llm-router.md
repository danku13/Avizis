# ADR-012: BYOK — LLM-роутер с адаптерами провайдеров

> Тип: ADR · Статус: принято (реализация — [CR-007](../cr/CR-007-byok-mvp.md)) · Связанное:
> [ADR-001](./ADR-001-llm-sdk-wrapper.md), [FR-900](../fr/FR-900-byok.md), [ADR-008](./ADR-008-demo-llm-dual-mode.md)

**Контекст.** Единственный путь LLM-вызовов в движке — singleton `z-ai-web-dev-sdk`
(ADR-001, `mini-services/avizis-agent/llm.ts`). Это блокирует три вещи: (1) пользователь не может
использовать собственные ключи и модели (OpenAI, DeepSeek, OpenRouter, локальный инференс
Ollama/LM Studio/vLLM); (2) четыре роли движка (планировщик, исполнитель, супервайзер, решатель)
ходят в одну и ту же модель — нельзя поставить дешёвую на частые малые вызовы и сильную на
исполнение; (3) воспроизводимость декларативная: снапшот прогона не фиксирует, какой моделью
выполнен каждый узел, — replay «той же системы» может молча уйти в другую модель, и аудит этого
не покажет. Ключи как класс в коде отсутствуют — вместе с политикой их хранения.

**Решение.**
1. **Слой роутера в `llm.ts`.** Интерфейс `LlmAdapter { id, label, chat(req: {system, user,
   role, json}) → {content, usage?} }`. Существующие ценности обёртки (extractJson/repairJson,
   таймауты, ретраи) — провайдер-агностичны и остаются над адаптерами, а не внутри них.
2. **Адаптеры MVP.** `zai` — дефолт, текущее поведение: без конфигурации система работает как
   раньше (обратная совместимость «из коробки»). `openai-compatible` — `baseUrl + apiKey +
   model`: один адаптер закрывает OpenAI, DeepSeek, OpenRouter, Groq, Together, Ollama, LM Studio,
   vLLM (все говорят на `POST {baseUrl}/chat/completions`, Bearer-токен).
3. **Роли.** `planner | executor | supervisor | decider`. Конфигурация per-role:
   `{adapter, baseUrl, model, apiKeyRef, temperature?}` с фолбэком: роль → дефолт-секция → zai.
4. **Ключи.** Хранение — только в серверном `data/llm-config.json` (chmod 600). API отдаёт
   конфигурацию с маской ключа (первые 3 + последние 4 симв.), полный ключ не возвращается
   никогда. Валидация при сохранении — пробным запросом. **Запрещено** появление ключей в
   `runs.json`, `RunSnapshot`, событиях, логах и экспортах — гарантия закреплена автоматическим
   тестом (поиск строки ключа в артефактах прогона). Для headless-запуска — env-переменные
   `AVIZIS_LLM_*` (бутстрап при отсутствии файла конфигурации).
5. **Provenance.** `RunSnapshot.llm = {role → {adapter, model}}` (без ключей) — фиксируется при
   старте прогона из разрешённой конфигурации; каждый LLM-узел получает `node.llm =
   {adapter, model}` в момент выполнения; в журнал при старте планирования — запись о провайдере
   и модели. Replay и MD-отчёт наследуют provenance автоматически.
6. **UI.** Модалка настроек: пресет провайдера, baseUrl, модель, ключ с show/hide, кнопка
   «Проверить подключение», per-role overrides в расширенном режиме; индикатор активного
   провайдера в тулбаре; в инспекторе узла — бейдж модели.

**Альтернативы.** Прямая интеграция SDK каждого провайдера в движок — дублирование логики
таймаутов/ретраев и жёсткая связность. Внешний LLM-шлюз (Vercel AI Gateway и т.п.) — лишняя
зависимость и дополнительная точка доверия для ключей. Отказ от BYOK — не решает ни стоимость,
ни локальный инференс, ни честность replay.

**Последствия.** Плюсы: свобода выбора (облако/локально), контроль стоимости и моделей по ролям,
честный replay (provenance в каждом узле), нулевая стоимость входа (дефолт = zai). Минусы:
критический путь LLM-вызова усложняется (роутер + адаптер + резолв конфигурации); ответственность
за ключи и лимиты провайдера переходит к пользователю (маски и валидация смягчают); тестовая
среда требует мок-провайдера (`scripts/mock-openai.ts`). Не в MVP: нативные адаптеры
anthropic/gemini, счётчики токенов и стоимости, стриминг ответов.
