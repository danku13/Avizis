> Формат: контекст → решение → альтернативы → последствия.
> Нумерация в хронологическом порядке сессии. Статусы: принято.

## ADR-001: LLM через z-ai-web-dev-sdk с repair-парсером JSON

**Контекст.** Прототип создан специально для тестирования `z-ai-web-dev-sdk`. Движку нужны
три LLM-роли (планировщик / исполнитель / супервайзер + позже decider), ответы приходят в JSON.
Наблюдаемые проблемы: обрывы массивов, висячие запятые, «reasoning» внутри массива nodes.

**Решение.** Единая обёртка-синглтон `llm.ts`: таймауты, ретраи, `repairJson()` (достраивает
незакрытые массивы/скобки, убирает висячие запятые), валидация схемы ответа с повтором запроса.

**Альтернативы.** Сырые вызовы SDK без обёртки — быстро ломаются на кривом JSON;
стриминговый парсинг — избыточен для прототипа.

**Последствия.** LLM-режим устойчив (тест `test-avizis-llm` пройден); любую новую роль
(decider в ADR-007) добавляем через системный промпт без изменения инфраструктуры.

## ADR-002: Движок агента как отдельный mini-service на socket.io (порт 3003)

**Контекст.** Next.js-фронтенд уже развёрнут через Caddy-шлюз (:81). Движок — stateful:
пауза/резюм, ожидание решений пользователя, поток событий. HTTP-запросы плохо подходят
для живого потока и долгоживущих состояний.

**Решение.** `mini-services/avizis-agent/` — отдельный bun-процесс с socket.io.
API: `run:start`, `run:control`, `run:load/delete`, `node:override/retry`,
`history:list`, `decision:resolve`, `decision:mode`. События: `graph:init`, `graph:adapt`,
`node:update`, `run:status`, `log`, `run:summary`, `decision:offer/resolved/mode`.
Запуск через double-fork (переживает завершение shell-команды).

**Альтернативы.** API-роуты Next.js + polling — дублирование логики трансляции состояния;
WebRTC/gRPC — избыточно.

**Последствия.** Движок живёт независимо от hot-reload фронтенда; клиент — тонкий
сокет-клиент в `src/lib/avizis/socket.ts`. Цена: отдельный процесс для мониторинга.

## ADR-003: Event-sourcing прогона (RunEvent-stream + fold на клиенте)

**Контекст.** Требуется живой просмотр И воспроизведение И версии графа И аудит.
Хранение «снимка состояния» порождает рассинхрон между live и replay.

**Решение.** Прогон = иммутабельная лента `RunEvent[]`. Клиент строит состояние
детерминированной свёрткой (`fold.ts`) до любого курсора — это даёт timeline-скраббинг,
версии v1/v2/v3 и «кадр» на любое событие из одного источника правды. Snapshot
(полная свёртка) хранится для загрузки из истории.

**Альтернативы.** Мутабельное состояние + отдельный audit-лог — два источника правды;
CRDT — не нужна коллаборация.

**Последствия.** Новые фичи (decision-события) добавляются как новые типы событий в fold —
playback «видит» ветки до/после решения бесплатно. Цена: полный рефолд при каждом тике
(для масштаба прототипа ок).

## ADR-004: React Flow (@xyflow/react v12) для визуализации графа

**Контекст.** Первый вариант — самописный SVG DAG (слоевой layout, пан/зум вручную).
Требования выросли: перетаскивание, MiniMap, зум-контролы, устойчивые взаимодействия —
самопись становилась узким местом.

**Решение.** Переписан `graph-canvas.tsx` на React Flow v12 (совместим с React 19):
кастомный узел-карточка `avizis` (статусная полоса, бейджи v2/изм., пульсация running,
dashed для динамических), рёбра smoothstep с цветовой кодировкой, Controls, MiniMap
(fuchsia для развилок), Background Dots. Позиции считаются тем же слоевым layout-ом,
авто-fitView при изменении сигнатуры узлов. `nodesDraggable/nodesConnectable=false`,
`deleteKeyCode=null` — граф только наблюдается.

**Альтернативы.** Доработка SVG-версии — ручной зум/пан/MiniMap; Cytoscape/D3 — тяжелее
интегрировать в React-19-стек.

**Последствия.** Меньше кода взаимодействия, больше — в визуальный язык. React Flow
атрибуция видима (лицензионно корректно). Тёмная тема стилизована в globals.css.

## ADR-005: Инспектор узла — модалка ≥50% ширины экрана

**Контекст.** Ранее инспектор был правой колонкой: на широких экранах — узко,
вход/выход длинные, чтение страдало. Требование: «не менее 50% ширины экрана».

**Решение.** `NodeInspectorModal` (shadcn/Radix Dialog): `sm:55vw / lg:58vw / xl:64vw`,
высота `86dvh`, мобильная ~92vw. Две колонки: мета (описание, причина, ошибка, тайминги,
зависимости) и Вход/Выход. Подвал: переопределить результат / повторить узел.
Открытие — клик по узлу, закрытие — Esc/фон. Radix-фиксы: sr-only Description,
замена ScrollArea на `div overflow-y-auto` в соседних панелях (клики «протекали» в граф).

**Последствия.** Один и тот же паттерн «модалка ≥50vw» переиспользован для decision-modal.
Плотность данных выросла, чтение входов/выходов стало комфортным.

## ADR-006: Модель развилок — все ветки в плане, статус 'discarded' у непринятых

**Контекст.** Нужна «мгновенная визуализация» изменения набора шагов при выборе варианта.
Если держать ветки «виртуально» и материализовывать выбор, придётся синтезировать новые
узлы на лету — сложнее для playback и аудита.

**Решение.** Узел `kind='decision'` с `DecisionState` (question, options[]: label/rationale/
nextSteps, status pending→offered→resolved, chosen, chosenBy: agent|user, reasoning).
Варианты реализуются в плане как параллельные цепочки узлов с `branchOf={decisionId,
optionId}`; итоговый узел зависит от хвостов всех веток. При `resolveDecision`: узел
done + output; sibling-ветки получают `status='discarded'` + `node:update` на каждую
(мгновенное гашение); зависимость от discarded-узла считается удовлетворённой, прогресс
считает только активные узлы; override не воскрешает погашенные ветки; остановка во время
ожидания — rollback узла в очередь.

**Альтернативы.** Материализация выбранной ветки на лету — нечестный playback;
полное удаление веток из графа — теряется объяснение «что могло быть».

**Последствия.** Пользователь всегда видит полную картину альтернатив; граница
«реализовано / не реализовано» — визуально явная (полупрозрачные серые карточки
«ветка не выбрана»). В графе появляются три состояния рёбер: fuchsia-пунктир (до выбора),
emerald (выбранная ветка), серый тихий (погашенная).

## ADR-007: Режимы решений «авто» / «ручной выбор», переключение на ходу

**Контекст.** Автономность агента должна быть управляемой: где-то агенту доверяем,
где-то хотим контроль. Требование: оба режима + смена без перезапуска прогона.

**Решение.** `decisionMode` хранится в RunSnapshot. Ручной: `handleDecisionNode` →
reasoning-фаза → emit `decision:offer` → движок «замерает» на promise
(`rt.pendingDecision`); фронт авто-открывает модалку выбора; `decision:resolve`
резолвит promise. Авто: LLM-роль DECIDER (JSON {optionId, reasoning}, fallback —
первый вариант) либо демо-скрипт. Смена режима в любой момент (`decision:mode`);
если сейчас ожидается выбор и включили «авто» — агент решает немедленно.
Stop/deleteRun разблокируют ожидание (rollback). Пробуждение после паузы — перевыпуск
развилки.

**Альтернативы.** Режим только на старте прогона — теряется сценарий «передумал и
делегировал агенту посреди ожидания»; выбор через toolbar-инспектор без модалки —
не соответствует требованию читаемости.

**Последствия.** Паттерн «пауза-на-обещании» переиспользуем для любых будущих
HITL-точек (аппрувы, лимиты бюджета). Модалка выбора дублируется входами: клик по
ожидающей развилке в графе и баннер в тулбаре.

## ADR-008: Двойной режим движка — demo (детерминированный) и llm (z-ai-web-dev-sdk)

**Контекст.** Концепцию надо показывать стабильно (демо) и при этом доказать работу
с реальным SDK (LLM). Полностью LLM-зависимый стенд нестабилен для быстрых проверок UI.

**Решение.** `RunMode='demo'|'llm'`. Демо: фиксированный сценарий «анализ аномалии»
(валидация → развилка из 3 стратегий → ветка → итог), где выходы зависят от выбранной
стратегии, агент в авто-режиме выбирает B с обоснованием. LLM: планировщик строит план
с ОДНОЙ развилкой (JSON c decision.options[].steps), sanitizePlan нормализует
ids/зависимости/ветки, executor/supervisor/decider — роли через системные промпты.

**Последствия.** UI-сценарии тестируются без затрат и флаков; интеграция SDK
подтверждается тестом `test-avizis-llm.ts`. LLM-JSON от планировщика проходит
тот же repair-конвейер (ADR-001).

## ADR-009: Смешанный выбор (multi-select) и certainty как самооценка понимания

**Контекст.** Пользователь должен видеть, насколько агент «понимает» задачу, и уметь принимать
не только одиночные, но и комбинированные решения (например, «кейс + статистика» в посте).

**Решение.** `DecisionState` расширяется: `selection: 'single' | 'mixed'` (mixed допускает
несколько id), `chosen: string[]`, `domain` (категория уточнения), `certaintyAfter` — на сколько
поднимется понимание после закрытия вопроса. `RunSnapshot.certainty` (0..1) публикуется событием
`run:certainty` при старте, разрешении каждой развилки (max(certainty, certaintyAfter)) и от
супервайзера LLM. Механика веток не меняется: при разрешении активны все выбранные ветки,
остальные гаснут (`discarded`); итог уже зависит от хвостов всех веток — mixed работает «бесплатно».
Валидация: unknown-id отбрасываются, single обрезается до одного.

**Альтернативы.** Синтез «гибридного» варианта агентом вместо multi-select — теряет прямую
семантику «что выбрано» в аудите; certainty только на финале — не показывает динамику.

**Последствия.** Frontend-хелперы `chosenIds/selectionMode` нормализуют старые прогоны
(chosen-строка → массив). Метр в тулбаре (качественная шкала) + «понимание: X% → ~Y%» в модалке.

## ADR-010: Эмерджентные развилки — вопросы, вставляемые по ходу выполнения

**Контекст.** Не все уточнения видны при планировании: агент должен анализировать результаты
КАЖДОГО шага (например, «запрос не задаёт формат публикации») и задавать вопрос именно тогда,
когда неоднозначность проявилась.

**Решение.** `insertDecision(anchorId, spec, reason)` в движке: узел-вопрос (dynamic, kind='decision',
domain/selection/certaintyAfter) + ветки вариантов как цепочки `branchOf`; ещё не начатые узлы,
ждавшие якорь, перепривязываются на хвосты ВСЕХ веток (невыбранные станут discarded — зависимость
удовлетворится). Триггеры: демо-сценарий «Напиши пост» — скриптованные вставки после ключевых
шагов (afterAny — первый раз); LLM — супервайзер в режиме `ask` возвращает вопрос с вариантами
(лимиты: ≤2 эмерджентных вопросов, не при открытой развилке). Вставка = новая версия графа
(graph:adapt) с причиной в аудите.

**Альтернативы.** Все вопросы на этапе планирования — агент не видит результатов шагов;
вопросы вне графа (чат) — теряется связка «вопрос ↔ последствия в шагах» и воспроизведение.

**Последствия.** Один и тот же механизм строит и плановые, и эмерджентные развилки; playback
показывает момент появления вопроса; демо-сценарий «Напиши пост» демонстрирует полный цикл
уточнения размытого запроса (certainty 0.2 → 0.95).
